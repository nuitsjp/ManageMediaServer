# スマートホーム基盤

Home Assistant Container を既存 Ubuntu に追加する初期基盤。基本設計書
`smart_home_architecture_v1_0.pdf` の第1段階を対象とする。Bluetooth ホストの準備までを含め、
SwitchBot の追加・24時間観測、Nano C6/MQTT、赤外線、HomeKit 公開、運用バックアップは後続段階で行う。

**現在の状態（2026年11月7日 JST）**：サーバーへの配置と Bluetooth 通知受信の検証は成功。
利用者から初期設定・MFA・Bluetooth 確認・SwitchBot 追加・24時間確認の完了報告あり。
初期設定完了は API でも確認済み。到達元制限は利用者確認済み。
11月7日の実際の再起動後にサービスの自動復帰を確認。コンテナー内からの通知受信の再検証が残る。

## 配置

既存メディアサービスと同じ配置規則を使う。設計書の `/srv/smarthome` 案は採用しない。

| 用途 | パス |
| --- | --- |
| Git 作業コピー | `/home/ubuntu/repos/ManageMediaServer` |
| Compose の管理元 | `docker/homeassistant/docker-compose.yml` |
| 本番 Compose | `/home/mediaserver/ManageMediaServer/docker/homeassistant/docker-compose.yml` |
| HA の `/config` 全体 | `/mnt/data/smarthome/homeassistant/` |
| 設定の初期値 | `config/homeassistant/configuration.yaml.example` |
| systemd | `/etc/systemd/system/homeassistant.service`、`smarthome-firewall.service` |
| root 実行用の保護コピー | `/usr/local/libexec/manage-smarthome/apply-smarthome-firewall.sh` |
| root 専用の実行時設定 | `/etc/manage-smarthome/firewall.env` |
| HA 専用 AppArmor | `/etc/apparmor.d/manage-smarthome-homeassistant`、`smarthome-apparmor.service` |
| 配置バックアップ・結果 | `/mnt/backup/smarthome/install-*/` |
| ログ | systemd journal とローテーション付き Docker ログ |

root 用の実行ファイル・設定を保護されたパスへコピーする方式は、既存の日次メンテナンスと同様。
Compose は `mediaserver` が実行する。HA コンテナ内は公式イメージの既定ユーザー root を使い、
`privileged` と Docker socket の共有は使わない。HA データは root 所有、ディレクトリーは 0700。
`/config` は認証情報や `.storage` を含むため、共有ディレクトリーや Git にコピーしない。

将来の Mosquitto/ESPHome/Nano C6 もコードはこのリポジトリー、本番配置は
`/home/mediaserver/ManageMediaServer`、データは `/mnt/data/smarthome/`、
バックアップは `/mnt/backup/smarthome/` に統一する。

利用者による再起動試験スクリプトは、再起動で消えた `/run/manage-smarthome` を必須としていたため
事前確認で停止し、追加の再起動は予約されなかった。`Unprotected directory` は権限不正ではなく未存在だった。
`prepare-smarthome-runtime.py` で不足する専用ディレクトリーとロックを作成するよう修正。
既存ロックの inode・内容・排他状態は保持し、書き込み可能な権限、所有者不一致、リンク、FIFO は拒否する。
実際の再起動が既に確認できているので、使い捨てスクリプトの `--check` で再起動せず復帰状態を検証できる。
この検証はsudoが必要。修正済み運用ファイルの本番配置はまだ旧版であり、必要時に専用の管理ファイル反映で更新する。

到達元制限の実機試験は、宅内端末で LAN アドレスに接続できることに加え、
スマートフォンの Wi-Fi を切ってモバイル通信＋Tailscale に切り替え、
`http://100.69.11.74:8123/` に接続できないことを確認する。
試験後は Wi-Fi に戻し `http://192.168.0.23:8123/` で再接続を確認する。
Tailscale の経路・ACL による拒否もあり得るため、この試験だけで FW の全規則を実証したとは扱わない。

再起動試験は既存サービスも一時停止する。利用者が都合のよい時刻に使い捨てスクリプトを実行し、
起動前の状態・管理ファイルのバックアップを保存してから再起動する。
これらの設定バックアップは HA の DB・認証情報を含む復旧用バックアップの代わりにはならない。
復帰後は boot ID の変化、HA/BlueZ/AppArmor/FW と既存サービス、HTTP、通知受信、
監査ログを確認し、利用者が SwitchBot の新しい測定値とログイン継続を確認する。

AppArmor 修正は `scripts/ops/repair-smarthome-bluetooth.sh` で反映する。
利用者に依頼する操作は、その時点で検証した使い捨てスクリプト1本にまとめる。
既存の HA データ、所有者情報、採用イメージは保持し、HA だけを停止・再作成する。
配置バックアップは `/mnt/backup/smarthome/bluetooth-repair-*/`。

## 初期構成と公開範囲

- HA 2026.10.4、linux/amd64 の manifest digest で固定。`stable` / `latest` を追従しない。
- 再起動は systemd が管理する。Docker 単独の自動再起動は無効とし、起動時に FW 適用を必須にする。
  Compose を foreground で監視し、HA 終了時は10秒後に再起動する。Docker の restart にも追従する。
- host network、`NET_ADMIN` / `NET_RAW` と `/run/dbus:ro` を Bluetooth 用に付与。
  D-Bus ソケットの `:ro` は管理メソッドを読み取り専用にするものではない。
- AppArmor は `manage-smarthome-homeassistant` を明示適用する。Docker の標準制限を基に、
  system bus の接続・購読と BlueZ の通信を許可する。ホスト全体の AppArmor、`docker-default`、
  seccomp の設定は変更しない。profile のロードを systemd で起動前の必須条件とする。
  ブロードキャスト受信は BlueZ のパス・標準通知インターフェースと `unconfined` の送信元ラベルに限定する。
  D-Bus の購読自体は `sender='org.bluez'` を指定し、他のサービスの通知を混ぜない。
- BlueZ のみ必要に応じて追加する。既存ホストの D-Bus 実装は交換しない。
- SQLite の詳細履歴は30日。設定 UI、履歴、モバイルアプリ、Bluetooth、zeroconf、Backup を有効化する。
  自動化・スクリプト・シーンの初期リストは空。機器・HomeKit・MQTT は自動登録しない。
- TCP 8123 は **enp1s0 からの 192.168.0.0/24 と loopback のみ**。
  IPv6 は loopback のみ。Tailscale、Funnel、WAN への公開は追加しない。
- `MMS-SMARTHOME` 専用チェーンを IPv4/IPv6 の INPUT 先頭から呼ぶ。
  HA は host network なのでメディア用 DOCKER-USER では保護できない。既存メディアのルールは変更しない。
- 今回は宅内 HTTP。HTTPS、HomeKit ポート、MQTT TLS、ESPHome API/OTA の公開は後続の設計・試験時に追加する。
- 管理者アカウントと MFA は利用者が画面から設定する。パスワードや MFA 秘密情報を導入スクリプトに渡さない。

## 導入と検証

管理ファイルの反映は `scripts/ops/deploy-managed-files.sh --smarthome-only` を使用する。
明示リストかつ Git 管理対象のスマートホーム関連ファイルだけを配置し、既存メディアサービスや
実行時設定を上書きしない。通常の全体反映とは別の選択肢として維持する。

初回導入本体は `scripts/ops/install-smarthome-foundation.sh`。
利用者が実行する必要がある場合は、リポジトリーの使い捨てスクリプト1本から呼び出す。

1. ソース、配置先、空き容量、ポート、既存データの有無、LAN アドレスを確認する。
2. 既存日次メンテナンスと同じ lock を取得し、OS 更新との並行実行を避ける。
3. `/mnt/backup` のマウントを確認し、変更前ファイル・既存サービス状態を保存する。
4. 固定 digest のイメージを取得し、対象の管理ファイルだけを配置する。
5. 新規の HA データディレクトリーに初期設定を配置する。既存データの移行には使わない。
6. BlueZ を追加・起動し、コントローラーが認識・給電されることを確認する。
7. 公式コンテナの `check_config` で設定を検証する。
8. IPv4/IPv6 の FW 制限を適用してから HA を起動し、自動起動を有効にする。
9. HTTP 応答、Docker health、コンテナー内からの D-Bus 接続・信号購読・BlueZ 列挙・
   アクティブなスキャン・実際の機器更新通知の受信、起動後の監査ログ、FW、
   既存サービス・コンテナの継続稼働を確認し、結果を保存する。

導入完了後、LAN のブラウザーで `http://192.168.0.23:8123/` を開き、所有者アカウントを作成して MFA を設定する。
一般利用者には別アカウントを使う。HA は自動化・家電操作を追加する前に次を実機確認する。

- LAN からの接続と、Tailscale 等の許可外経路からの TCP 8123 接続拒否。
- Docker healthcheck、Bluetooth 統合でのアダプター認識。
- 既存の Immich・Jellyfin・Token Monitor と既存タイマーに支障がないこと。
- サーバー再起動後の復帰。再起動は既存サービスにも影響するため、実施時刻を調整する。

サーバー上だけの HTTP 応答と FW ルール確認では、別端末からの拒否・再起動試験を代替できない。
今回の準備・静的検証と、本番反映後の動作確認は区別して記録する。

## 切り戻しと運用開始条件

導入中に失敗した場合、スクリプトは追加した HA の停止・コンテナ削除、自動起動解除、
専用 FW ルール削除、管理ファイル復元を試みる。新規 HA データは `install-*/failed-data` に退避する。
BlueZ パッケージと取得イメージは残る。導入前に Bluetooth が停止・無効ならその状態へ戻す。
apt 処理そのものの失敗やホスト障害による中断では手動確認が必要。復元結果とエラーは実行出力で確認する。

導入成功後の撤去は、HA を先に停止・自動起動解除してからコンテナと専用 FW を解除する。
データ・バックアップは保持し、秘密情報を含む `.storage` や DB を不用意に削除しない。
利用者に管理者操作を依頼する場合は、その時点の状態を確認した使い捨てスクリプト1本で実施する。

**この段階では自動バックアップ・監視通知・機器の連携は未導入。常用開始前に後続段階を完了する。**
HA の Backup 機能で暗号化・復号キー保管・整合性を確保し、周辺サービスのデータを別途保存する。
日次7世代＋週次4世代、筐体外暗号化コピー、復元試験を設計書に従って実装する。
既存のメディアバックアップは HA を対象に含まない。稼働中 SQLite の単純コピーで代用しない。
更新は手動とし、変更前バックアップ、リリースノート確認、設定検証、動作確認を行う。
既存の `media-app-update.sh` に HA は追加しない。
